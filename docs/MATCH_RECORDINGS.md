# Live match recordings

Development builds automatically record newly started live matches in
`<app data>/match-recordings/`. On macOS this is normally
`~/Library/Application Support/com.sturdyrobot.openfootmanager/match-recordings/`.
Restart the development application after installing this change, then start a
match. Previous matches and already-running sessions cannot be recovered by it.
Each session has its own timestamp/UUID filename, logged at startup. Files remain
after the match finishes; partial matches can also be inspected.

To choose another directory (or opt into recording in a release build), launch
with `OFM_MATCH_RECORDINGS_DIR` set. For example, from the repository root:

```sh
OFM_MATCH_RECORDINGS_DIR=/tmp/ofm-matches npm run tauri dev
```

Recording is local and independent of save files. It does not advance a match or
send data anywhere. A write failure is logged and disables that recording while
the game continues. There is no automatic deletion of recordings.

## Inspect and reproduce

The inspection command uses the same `LiveMatchSession` that the desktop uses,
including AI decisions. It does not use the instant `sim-bench` engine.

```sh
# Teams, score, completeness, command counts and the full event timeline.
cargo run --manifest-path src-tauri/Cargo.toml -p ofm_core --example match_recording -- /path/match.jsonl

# Re-run and compare every minute, accepted AI command and post-command state.
cargo run --manifest-path src-tauri/Cargo.toml -p ofm_core --example match_recording -- /path/match.jsonl --verify

# Last state at minute 55, its events, user commands and AI commands.
cargo run --manifest-path src-tauri/Cargo.toml -p ofm_core --example match_recording -- /path/match.jsonl --minute 55

# Export the recorded initial state and ordered snapshots as JSON.
cargo run --manifest-path src-tauri/Cargo.toml -p ofm_core --example match_recording -- /path/match.jsonl --snapshots > snapshots.json
```

Inspection outputs JSON. Verification exits nonzero on a mismatch and identifies
the first differing entry/minute. Engine/RNG version mismatches refuse verification;
recorded snapshots remain inspectable. Files over 64 MiB, unknown schema versions,
malformed lines and incomplete entries are rejected. Partial matches are valid and
explicitly reported as incomplete.

## What is captured

The JSONL header contains format version, app version, a compiled engine-source
fingerprint, RNG identity and seed (as a decimal string), initial teams, benches,
tactics, set-piece assignments, match configuration, controlled side and AI profiles.
Each subsequent line contains either:

- `step`: the authoritative minute result, accepted AI commands and snapshot after AI.
- `command`: an accepted user command and its resulting snapshot.

Failed commands do not enter the recording. Fast-forward and run-to-completion
use the same recording path. Floating-point JSON parsing preserves exact values;
unordered sent-off sets are compared without depending on iteration order.

This is an engine diagnosis and event-replay tool, not a video recorder. It does not
capture playback speed, camera framing, kits or the exact rendered frame from which
the interface started each clip. Visual coordinates generated by the presentation
layer are not authoritative engine data. Team talks that affect the broader game
but do not mutate the live match are likewise outside this recording.

## Comparing a future engine change

Keep the original recording as evidence of the old behaviour. Its events and
snapshots can always be inspected with the same schema. Exact verification is tied
to the engine fingerprint and dependencies; do not bypass that check and claim the
old match was reproduced after changing the engine. A future comparison runner can
reuse initial inputs while reporting changed results explicitly.
